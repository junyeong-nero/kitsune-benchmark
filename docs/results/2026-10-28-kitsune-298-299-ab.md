## Result in one paragraph

On the read-only tab-inventory saturation workload, the candidate cut the Kitsune
MCP process's CPU per request from **12.0–12.1 ms to 0.74–0.76 ms at one client**
(6% of the baseline). Its MCP CPU per request was lower than every baseline arm at
every concurrency, the predeclared criterion. Throughput rose from 73 to 560–567
requests/s at one client and from 265–340 to 1,520–1,624 at eight. p95 at one
client fell from 20.3–20.5 ms to 1.9–2.0 ms. In the same runs Playwright MCP served
406–425 requests/s at one client; Kitsune's throughput relative to Playwright rose
from 0.17–0.56× to 1.37–2.87× across all levels. All 96 arms completed with zero
request errors.
With the extension change, every candidate start kept its first bridge connection
(24/24); every baseline start dropped it (24/24). This is a deployment/workload
result for one tool call, not an agent task-success or general browser ranking.

## Completion and integrity

**4/4 runs, 96/96 arms valid, 1,747,864 measured requests, zero request errors.**
Kitsune: 153,503 baseline and 825,893 candidate requests; Playwright: 768,468. Every
arm passed the shared-tab and one-Firefox-tree checks, and every response matched
the two-tab baseline. Two measurement warnings, neither in a candidate arm:

- Run 2, Playwright 32 clients (repeat 2): `host_cpu_slower`. The canary right after
  the preceding Kitsune 32-client arm took 0.149 s, 1.57× the run's first; after the
  Playwright arm it was back to 0.098 s. A transient after the heaviest arm, on a
  control arm.
- Run 4, baseline 32 clients (repeat 1): `sampling_cadence_degraded`. The resource
  sampler took two load samples 30 s apart while the host was saturated. CPU over
  the window is still the difference of cumulative counters, but RSS and component
  figures for that arm are coarse. Request metrics are unaffected.

All other canaries stayed within 0.97–1.15× of their run's first (0.090–0.095 s).

- The candidate's owned CPU per request is 1.5–3.5 ms, against 2.6–3.4 ms for
  Playwright's server and Firefox in the same runs. Its MCP processes still use
  about half to two thirds of it: 0.75 ms per call at one client, 2.1–3.2 ms at
  16–32 clients. The rest of the MCP dispatch, serialization and the HTTP client
  built per call were not profiled.
- At 8–32 clients the candidate's owned processes use 3.9–4.6 cores (baseline
  5.9–6.9), but whole-machine CPU is 6.9–7.7 of 8 cores (baseline 7.9–8.0), so its
  decline past 8 clients can be host contention as much as a Kitsune limit. Bridge
  and Firefox CPU per request is 0.50–0.58 ms each at 8–32 clients (baseline
  0.78–1.07); each request is still a new TCP connection to the HTTP/1.0 bridge.
- Mean RSS fell at most levels, but it varies run to run (macOS reclamation, swap)
  and the per-client process layout is unchanged: about 65 MiB per client.
- Whole-machine CPU minus owned and driver CPU was 0.8–3.5 cores. A separate
  40-second diagnostic run of the candidate at 8 clients put the remainder at the
  machine's idle background (117% vs 97% in the idle window); this probe cannot
  attribute it further.

## Extension connection at startup (#299)

`bridge.log` of every Kitsune arm, counting `Browser extension connected
(generation N)`:

- **Baseline: 24/24 arms dropped the first connection.** 16 settled on generation
  2 and 8 on generation 3; the harness's stability wait accepted generation 2 or 3.
- **Candidate: 24/24 arms connected once (generation 1) and kept it.**

This is the browser check in #299's acceptance list: a fresh web-ext start logs a
single generation. Startup readiness is not part of the measured load.

## Interpretation and limits

- The candidate changes the cost of **each bridge call** in the MCP server
  (≈11 ms of CPU per call removed). In model-driven tasks, where calls are seconds
  apart, that is negligible next to model turns. The effect matters for concurrent
  clients sharing one browser, high-frequency tool use and the Python API, which
  shares the same bridge client. No taskset-v3 score changes.
- Closed-loop saturation with coordinated omission; one workload
  (`browser_tabs list`), no navigation, DOM extraction or screenshots; one fanless
  host; two runs per build. Ranges are descriptive.
- The candidate keeps a new client and TCP connection per call, the same timeouts,
  headers and error handling, and adds no reuse or retries. Kitsune's tests passed
  on it: 827 unit tests (143 opt-in browser tests skipped), all 44 Node tests, and
  the real-browser connection-diagnostics and core suites (26 tests) on Firefox 156.
- Not compared against the 2026-10-26 numbers as an A/B baseline; the earlier
  figures are consistent with run 1 and run 4 (68.2 vs 72.7–73.4 req/s at one
  client) but used Python 3.12.6.

## A1 — Native key actions silently do nothing

**Owner:** Kitsune. **Suggested label:** bug. **Suggested priority:** P1.

### Benchmark evidence

All three crowded `ui-editor` variants eventually passed the broad append/save
grader, but the transcripts show failed editing attempts:

| Crowded editor, 3 variants | Playwright | Kitsune |
| --- | ---: | ---: |
| MCP calls | 34 | **102** |
| Input tokens | 781,375 | **1,048,196** (+34.1%) |
| Variant 1 calls | 9 | **60** |
| Variant 2 calls | 16 | **34** |

In variant 1 Kitsune tried 18 `ArrowLeft` calls, then 18 `Shift+ArrowLeft` calls,
spaces and Backspace. Variant 2 tried 20 `ArrowLeft` calls. Tool results were
successful, but the agent eventually reported that the editing keys had no
effect and saved the appended sentence without a separator. Do not attribute
all 68 extra calls causally to this bug without an A/B; the repeated recovery
loops are direct evidence of its practical cost.

### Deterministic no-model reproduction

Fresh private Firefox, pinned Kitsune
`83acfe92272cd5bb0909785d7d821d05136710d0`, standard core MCP tools. A local page
contains `<input value="abcdef">` and a contenteditable `abcdef`, with the
caret initialized at the end. Page-side telemetry records text, selection,
focused element and key events, independently of MCP snapshots.

- Input: ArrowLeft, Shift+ArrowLeft, Space, Backspace — **4/4 no state change**.
- Contenteditable: those four plus Enter — **5/5 no state change**.
- Each call returns `isError: false` and a payload such as
  `{"ok":true,"key":"Backspace","target":"input"}`.
- Events arrive with `isTrusted: false`; text and caret/selection remain unchanged.
- The same nine cases through pinned Playwright MCP change the state as expected:
  Backspace makes `abcde`, Space inserts a space, ArrowLeft moves the caret and
  Shift+ArrowLeft selects `f`; Enter inserts a line break in the editor.
- End when already at the end, and Enter in an input outside a form, are controls
  where no change is expected; they are **not** counted as failures.
- A fresh Kitsune-only repetition reproduced all nine no-ops. The Playwright
  control is the successful separate probe, not the aborted reference setup in
  the initial combined probe.

### Source evidence / expected behavior

`extension/content/content.js:3509` dispatches synthetic keydown/keyup events.
Text insertion is implemented only when an explicit `text` argument is supplied.
The core `browser_press_key` adapter (`src/kitsune/playwright_tools.py:343`) passes
key/modifiers but no text. Synthetic key events do not supply native editing
behavior by themselves.

Proposed acceptance criteria:

- Implement supported default caret/selection/editing actions, respecting
  `preventDefault`, modifiers and selection ranges, or explicitly report that
  the requested effect is unsupported rather than implying completion.
- Preserve page keyboard handlers (the custom slider/sortable widgets work via
  handlers); avoid duplicate edits when the page handles an event itself.
- Test input, textarea and contenteditable, and test actual state changes rather
  than only event dispatch or `ok`.
- Retain the background/user-focus guarantees: do not fix this by stealing the
  user's foreground input.
- Rerun editor tasks with a state-based insertion/separator/selection assertion,
  plus existing coexistence tests.

Related, not identical: closed [#159](https://github.com/junyeong-nero/kitsune/issues/159)
covered click focus and insertion position; closed
[#173](https://github.com/junyeong-nero/kitsune/issues/173) covered key-name normalization.
Open [#257](https://github.com/junyeong-nero/kitsune/issues/257) reports Enter search
submission on Naver. These probes do **not** establish the cause of that live-site
failure, but provide a deterministic keyboard-default-action case to cross-link.

## A2 — Upstream MCP failure is hidden by the tool-filter process

**Owner:** kitsune-benchmark. **Suggested label:** bug. **Suggested priority:** P1.

The blocking-MCP correction fixes startup racing, but does not fix relay process
lifecycle. In `kitsune_benchmark/mcp_tool_filter.py`:

- `relay_output()` ends when the upstream stdout closes.
- The main thread remains blocked on the client's stdin.
- The filter keeps its own stdout open while the real server is gone.
- After client EOF, it waits for the child but unconditionally returns **0**.

### No-model reproduction

A fake upstream replies to initialize, then exits **2** on `tools/list`:

```text
initialize response forwarded: yes
upstream exit: 2
filter exit while client stdin remains open: none (still running)
stdout reply or EOF after upstream exit: neither
filter exit after client stdin closes: 0
```

This is reproducible without a browser, credentials or model. It can turn a
short setup failure into a request/run timeout and obscure the cause. The full
suite's failed native seed produced an empty catalog and lasted to the agent's
180-second timeout; the lifecycle defect is consistent with that symptom, but
no original process-lifecycle trace was captured to prove it was its sole cause.

Proposed acceptance criteria:

- Upstream EOF/nonzero exit ends the filter promptly even if client stdin stays
  open; propagate failure rather than returning 0.
- Resolve pending requests with a bounded diagnostic or close the transport
  so the client can fail immediately.
- Add an integration test keeping client stdin open after an upstream
  initialize-then-tools/list failure; assert bounded exit, nonzero status and
  no orphan process.
- Stop before further model work when the required catalog/fixture is absent.
- Preserve **sanitized** setup error fields (stage/tool/code/duration) in native
  evidence. Currently `NativeSession.tool()` raises a generic error and the
  saved setup failure loses the response body. Do not publish raw URLs/tokens.

The local blocking-startup and full-suite stop changes are already implemented
and tested; they should be published as fixes, not re-filed as unfixed bugs.
This child-exit handling is a distinct remaining defect.

## A3 — Intermittent failure while creating the fourth starting tab

**Owner:** Kitsune. **Suggested label:** investigate/bug candidate.
**Suggested priority:** P2; not a confirmed regression.

Personal `pb-tabs-01`, variant 2, fresh isolated v0.4.1 browser/bridge:

- The `browser_tabs(action="new")` call for the fourth starting tab returned a
  native tool error after **15.27 seconds**. The error response body was not
  retained, so do not invent its error code or call it a proven bridge timeout.
- Fixture preparation remained incomplete; no agent tool calls occurred.
- Several extension connection generations appeared during startup. This is
  correlation, not proof that reconnection caused the tab error.
- The run was externally unscorable and the suite stopped. One explicit retry
  later passed. Three no-model fresh-profile seeds also passed in 2.3–2.6 s.

Proposed investigation:

- Repeat a four-tab seed on the exact pin under isolated and concurrent-target
  load; record safe request identifiers, extension generation and lifecycle
  timestamps around the failure.
- Distinguish HTTP readiness, WebSocket readiness and tab/document readiness.
- On ambiguous tab-creation failure, verify existing tab state before any retry;
  **do not blindly replay a potentially dispatched create action**.
- Bound the failure and return actionable retryability/outcome information.

Related [#258](https://github.com/junyeong-nero/kitsune/issues/258) is about the
first call after automatic replacement of a shared bridge. This benchmark used
a fresh private bridge and its failure log contains **no `/api/shutdown`**;
therefore do not assume it is the same issue. Cross-link first, merge only if
reproduction establishes a shared mechanism.

## A4 — Table token cost tracks model rounds, not just tool-call count

**Owner:** kitsune-benchmark for the hypothesis; Kitsune changes, if any, follow
validation. **Suggested priority:** P2. **Not a confirmed tool bug.**

All paired `ui-table` tasks succeeded. Aggregates across three data variants:

| Layout | Target | MCP calls | Model requests | Input tokens |
| --- | --- | ---: | ---: | ---: |
| Crowded | Playwright | 42 | 21 | 566,953 |
| Crowded | Kitsune | 43 | **36** | **866,012 (+52.7%)** |
| Isolated | Playwright | 47 | 20 | 288,077 |
| Isolated | Kitsune | **41** | **31** | **401,723 (+39.4%)** |

Kitsune's snapshot text was actually **smaller** in both layouts. The evidence
therefore does not justify "truncate snapshots more" as the identified fix.
More model requests resend fixed context and accumulated history; that is a
measured association, not proof of why the agent serialized its actions.

Proposed hypothesis/experiment:

- Investigate whether compact, actionable post-action state and scoped reads
  reduce separate verification/model rounds without losing row reachability.
- Inspect independent-read grouping and repeated observations; do not batch
  state-dependent writes or clicks whose refs can change.
- Compare baseline and candidate on the same pin/model/harness, with repeated
  and counterbalanced trials. Pre-agree success/safety and input-token adoption
  criteria; count model requests as well as MCP calls and response characters.
- Retain all table rows/values and the formerly missing crowded-v1 row. Do not
  undo the correctness fix merely to reduce observation size.

Related [benchmark #4](https://github.com/junyeong-nero/kitsune-benchmark/issues/4)
tracks controlled measurement broadly. [Kitsune #262](https://github.com/junyeong-nero/kitsune/issues/262)
concerns bounded snapshots for long pages; this table finding is a distinct,
more specific round-trip hypothesis, not proof of unbounded output.

Secondary observation, not a separate issue yet: crowded `ui-infinite` uses
52 vs 32 calls and 32 vs 22 model requests (Kitsune vs Playwright), with more
find/hover/wait operations. Native default-key behavior and readiness/observation
choices should be isolated before splitting that into another optimization issue.

## Existing issues to update, not duplicate

### B1 — Core recovery hints must name supported parameters: Kitsune #255

[Open #255](https://github.com/junyeong-nero/kitsune/issues/255) already covers
`not_fillable` suggesting `mode="editable"`, which the core tool schema does not
expose. The fixed-pin benchmark provides additional evidence outside Papago:

- Isolated `ui-slider` variants 0, 1, 2 each fail one `browser_fill_form` call.
- The target is a custom `div[role=slider]`, not a fillable input. All three
  eventually succeed through other actions.
- All three failures contain the unsupported `mode="editable"` hint; it is also
  irrelevant to an ARIA slider.

Add these cases to #255 and test recovery guidance against the actual published
schema and widget role. A generic custom slider rejecting text fill is **not by
itself** a demonstrated new bug; the invalid/misleading repair instruction is.

### B2 — Ownership-aware cleanup and view scoring: benchmark #9

[Open #9](https://github.com/junyeong-nero/kitsune-benchmark/issues/9) already
proposes v2 as the next taskset's primary safety rule. New evidence:

- Three full-suite personal misses (`pb-research-03` v1; `pb-safe-02` v1/v2)
  are functionally successful, preserve starting tabs, and fail only for closing
  an agent-opened tab. Scores change **69/72 → 72/72** under v2.
- The coexistence `pb-safe-02` miss similarly changes **23/24 → 24/24** under v2.
- The composite v3 view contract inherits v1 task success, so it reports
  **23/24** even though the shown view stayed unchanged in **24/24** runs.

Implement next-taskset primary scoring, with separate functional, ownership,
view and input dimensions. Keep v1 and its historical scores intact; do not
retroactively relabel results or imply v3 actually passed 24/24 in this run.

### B3 — CAPTCHA-policy confounding: benchmark #10

[Open #10](https://github.com/junyeong-nero/kitsune-benchmark/issues/10) already
identifies this problem. The remaining isolated Gallery failure (`mm-text` v1)
was one snapshot followed by explicit refusal, not an attempted wrong answer or
a failed screenshot tool. The other five Kitsune layout/variant instances passed.

Add the new pinned-cohort evidence. For a new taskset, use an ordinary product
label/serial-number reading task, or report the existing puzzle separately as a
policy probe. Do not disguise a human-verification challenge or optimize toward
bypassing refusal; the benchmark needs to measure the intended capability.
